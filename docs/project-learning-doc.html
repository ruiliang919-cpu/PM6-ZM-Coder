心跳处理详解 (handleHeartbeat)

心跳是最频繁的消息类型。每次心跳做三件事：
① 更新 Redis 中的 DevBaseDeviceTCPVo 缓存（onlineStatus、lastTime、version）
② 判断设备是否从离线恢复上线，如果是则清理故障缓存
③ 通过 DeviceStatusPushService 推送 WebSocket 状态变更 
// MqttMessageHandler.java:104-172 心跳处理核心逻辑
private void handleHeartbeat(Integer deviceNo, String payload) {
    Heart heart = JSONUtil.toBean(payload, Heart.class);     // ① 解析心跳JSON
    DevBaseDeviceTCPVo tcp = tcpManager.getOneByCache(deviceNo); // ② 从Redis取设备缓存

    boolean wasOffline = tcp.getOnlineStatus() == 0;
    boolean shouldGoOnline = heart.getData().getOnline();

    if (wasOffline && shouldGoOnline) {
        // 设备从离线恢复 → 完整更新缓存 + 清理故障
        tcp.setOnlineStatus(1);
        redisTemplate.opsForValue().set("zm:create-tcp:" + deviceNo, tcp, 2, DAYS);
        redisTemplate.delete("zm:fault:" + deviceNo + ":0xAAAA");
    } else {
        // 设备已在线 → 仅刷新 lastTime
        tcp.setLastTime(new Date());
        redisTemplate.opsForValue().set("zm:create-tcp:" + deviceNo, tcp, 2, DAYS);
    }

    deviceStatusPushService.pushDeviceStatus(deviceNo, tcp); // ③ WebSocket推送
}

离线处理详解 (yz 方法 — connect 事件)

当设备 MQTT 连接断开时，yz() 方法处理离线逻辑：

  • 设置 onlineStatus = 0，更新 Redis 缓存
  • 清除该设备的所有故障告警缓存 (SCAN 替代 KEYS 避免阻塞)
  • 写入离线告警到 DevFaultRecord 数据库表
  • WebSocket 推送离线状态 + 告警

2.3 缓存体系 — 系统的"记忆"

职责

用 Redis 缓存所有高频读取的设备数据，避免每次都查 MySQL。Key 类是整个缓存体系的统一访问入口。

Redis Key 五层结构

zm:create-tcp:{deviceNo} ← 设备连接信息 (DevBaseDeviceTCPVo) zm:queue:zm:cache:1:{ip}:{id}:0x0000 ← 遥控数据 (boolean[] 线圈状态数组, 845位) zm:queue:zm:cache:3:{ip}:{id}:{addr} ← 遥测数据 (BigDecimal/short[]/List) zm:queue:zm:cache:63:{ip}:{id}:{addr} ← 遥调数据 (配置参数、控制参数) zm:fault:{deviceNo}:{addr} ← 故障告警缓存 zm:power:power:{deviceNo} ← 功率缓存 zm:power:loss:{deviceNo} ← 损耗缓存 zm:order:{deviceNo}:1:{addr} ← 待发送指令标记 zm:select:group:{deviceNo} ← 分组选择状态 zm:select:loop:{deviceNo} ← 回路选择状态 zm:workModule ← 工作模式 (Hash) zm:global:module:select ← 全局模式 ("on-the-line" = 远程控制中) zm:global:scene:select ← 全局场景选择

2.7 设备在线检测 — 心跳保活机制

职责

定时扫描 Redis 中所有设备缓存，将超时未心跳的设备标记为离线。

双保险机制

机制一：MQTT 心跳 (主动上报) 设备每 N 秒发送 heart 消息 → MqttMessageHandler.handleHeartbeat() → 刷新 lastTime 机制二：定时扫描 (被动检测) DeviceOnlineCheckTask (每30秒) → SCAN zm:create-tcp:* → 检查 lastTime │ ├── lastTime 超过 60秒 → 二次确认(重新读Redis) → 标记离线 └── lastTime 未超时 → 跳过

DeviceOnlineCheckTask (ruoyi-zm/mqtt/DeviceOnlineCheckTask.java) 使用 SCAN 遍历替代 KEYS，避免阻塞 Redis。离线阈值 60 秒，采用二次确认防止竞态条件。

3.3 架构设计模式总结

🏭 工厂模式

AddrHandlerFactory + Spring 自动注入，20+ 地址处理器按名称路由，新增零侵入

📦 代理/门面模式

Key 类封装全部 Redis 操作，上层代码无需关心 Key 格式和 Redis API

🔄 发布/订阅模式

MQTT 本身就是 Pub/Sub，设备上报 → 服务端订阅处理；控制下发 → 发布到设备

📋 命令队列模式

WriteQueueCache + Redis List 实现指令队列，异步解耦控制指令与发送

🛡️ 守卫模式

ModuleGuard 在每个控制入口检查远程模式，防止误操作

💾 缓存穿透保护

Key.getCreateTCP() 先查 Redis，未命中查 MySQL 并回填，避免缓存穿透
